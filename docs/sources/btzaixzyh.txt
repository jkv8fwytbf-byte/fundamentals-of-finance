### ⚠️ "Requests" no longer exist

The 500-requests/month model died in June 2025 ([cursor.com/blog/new-tier](https://cursor.com/blog/new-tier)). Since then it is **token-based billing against two separate monthly pools** ([cursor.com/docs/models-and-pricing](https://cursor.com/docs/models-and-pricing)):

1. **Cursor Models pool** — Grok 4.6, Grok 4.5 (jointly trained by Cursor and SpaceXAI), Composer 2.5. Very generous allowance; this is the pool that effectively doesn't run out.
2. **Other Models pool** — Anthropic (Opus/Sonnet/Haiku/Fable), OpenAI GPT-5 series + GPT-5 Codex, Google Gemini 2.5→3.8 Flash, Meta, Moonshot, Z.ai. **Charged at the model's raw API price per million tokens.** This is the pool that empties. Teams/Enterprise pay a **+$0.25/M token surcharge** on third-party models.

**Auto mode** has three settings — Cost, Balance, Intelligence — and bills at the list price of whichever model it routes to.

Practical read for you: on Pro at $20, you get unlimited-ish Composer 2.5/Grok plus roughly $20 of Claude/GPT tokens. Heavy agent use on frontier models will exhaust that in days, and then you're on overage.

### BYOK and OpenRouter

Official BYOK providers ([cursor.com/help/models-and-usage/api-keys](https://cursor.com/help/models-and-usage/api-keys)): **OpenAI, Anthropic, Google, Azure OpenAI, AWS Bedrock**. Bedrock additionally supports IAM-role-based config ([docs](https://cursor.com/docs/customizing/aws-bedrock)).

**OpenRouter is not officially supported**, but works via the "Override OpenAI Base URL" setting. Per [OpenRouter's own Cursor cookbook](https://openrouter.ai/docs/cookbook/coding-agents/cursor-integration): paste your `sk-or-...` key into the OpenAI API Key field, enable the base-URL override, and set it to **`https://openrouter.ai/api/v1/cursor`** — the `/cursor` suffix is mandatory; the plain `/api/v1` endpoint breaks tool calls. Then add models manually (e.g. `~anthropic/claude-opus-latest`, `deepseek/deepseek-v4-flash`).

**What BYOK/base-URL override disables — this is the important part:**
- **Tab completion never uses your key.** It always runs on Cursor's in-house models.
- **Auto and Composer 2/2.5 modes may not route through your key** (OpenRouter docs say so explicitly).
- There is **no Anthropic base-URL override** — only OpenAI. Long-standing open feature request ([forum](https://forum.cursor.com/t/missing-anthropic-base-url-override-in-cursor-byok/158805)).
- 🔴 **"Cursor's Zero Data Retention policy does not apply when you use your own API keys."** Direct quote from the BYOK help page. Data handling reverts to your chosen provider's terms. For a *private* valuation system this matters more than the cost saving.

### MCP

Config at `.cursor/mcp.json` (project) or `~/.cursor/mcp.json` (global) ([docs](https://cursor.com/docs/context/mcp)). Three server types: CLI (`command`/`args`/`env`), remote HTTP/SSE (`url`/`headers`), and OAuth (`auth` object with client ID/secret/scopes). Transports: **stdio, SSE, Streamable HTTP**. **One-click install** exists via the Cursor Marketplace for official plugins, plus `cursor.directory` "Add to Cursor" buttons with OAuth. No documented tool-count cap.

### Agent mode / Plan mode

Switch with the mode picker or **Shift+Tab** ([docs](https://cursor.com/docs/agent/modes)). Plan Mode: agent asks clarifying questions → reads codebase → produces a written implementation plan → you edit it in chat or as a markdown file → click to hand off to Agent for execution. Recommended for multi-file work and architectural decisions; skip it for small edits. **This is exactly the right workflow for a beginner building a system they don't fully understand yet** — you review the plan in plain English before any code is written.

### Cloud / Background Agents

[cursor.com/docs/cloud-agents](https://cursor.com/docs/cloud-agents): isolated cloud VMs with full dev environments, no local machine needed.
- **GitHub & Bitbucket:** comment `@cursor` on a PR or issue → clones repo, works on a branch, pushes back for review.
- **Slack:** `@cursor` in a channel, with progress notifications.
- **Web/mobile:** cursor.com/agents, Cursor iOS app, "Cloud" option in desktop, plus Linear and Azure DevOps triggers.
- **MCP servers work inside cloud agents** — so your Neon/Pinecone MCP tools are available to them.
- Unlimited parallelism; you set a spend limit. Billed at **standard API pricing for the selected model**, drawing from your usage pool.

Recent additions: **Origin** (Cursor's own git hosting with GitHub sync, 17 Aug 2026), **self-hosted machines** (2 Sep 2026, incl. AWS Lambda/Vercel), and **Cursor Projects** (10 Sep 2026) where a coordinator agent plans and delegates to parallel subagents without writing code itself ([changelog](https://cursor.com/changelog)).

### BugBot

[cursor.com/docs/bugbot](https://cursor.com/docs/bugbot). Reviews PR diffs on GitHub/GitLab/Bitbucket/Azure DevOps, leaves inline comments with fix suggestions, reads existing PR comments to avoid duplicates, and can spawn a Cloud Agent to apply the fix. Auto mode runs on every PR update; manual via `cursor review` or `bugbot run`. Effort levels: Low / Default / High / Smart.

**Pricing: the $40/seat/month subscription was killed** — since ~8 June 2026 it is pure usage-based billing ([cursor.com/blog/may-2026-bugbot-changes](https://cursor.com/blog/may-2026-bugbot-changes)). Individuals: draws from included usage, then on-demand spend. Teams: entirely on-demand spend. Third-party estimate: **~$1.00–1.50 per run**, and **the billing unit is a run, not a PR** — it re-reviews the full diff on every push, so an iterative branch bills several times ([getoptimal.ai](https://getoptimal.ai/blog/cursor-bugbot-pricing)).

### Privacy / ZDR

[cursor.com/docs/enterprise/privacy-and-data-governance](https://cursor.com/docs/enterprise/privacy-and-data-governance) and [cursor.com/security](https://cursor.com/security): with Privacy Mode on, code is never used for training, and Cursor holds **zero-data-retention agreements with all model providers**. Certifications: **SOC 2 Type II, ISO/IEC 27001:2022, ISO/IEC 42001:2023, AIUC-1, GDPR/DPA**. Privacy Mode is **on by default only for Enterprise**; individuals must enable it. CMEK and data residency are Enterprise-only. Again: **ZDR evaporates if you BYOK.**

### Terminal, git panel, diff review

Cursor is a VS Code fork, so you inherit the integrated terminal, the Source Control panel, and side-by-side diffs unchanged. Agent edits land as a reviewable diff you accept/reject per hunk before commit. For a beginner this is the single biggest advantage over terminal-only tools: **you can see what changed before it's yours.**

### ⚠️ Scheduled jobs — Cursor DOES have them

Your premise ("whether it can run scheduled jobs (no?)") is out of date. **Cursor Automations** shipped 5 March 2026 ([blog](https://cursor.com/blog/automations), [docs](https://cursor.com/docs/cloud-agent/automations), [changelog 03-05-26](https://cursor.com/changelog/03-05-26)), improved 18 June 2026.

- **Triggers:** recurring intervals or **custom cron expressions**; GitHub (PRs, pushes, labels, CI completion, reviews, workflow runs); GitLab/Bitbucket; Slack (messages, emoji reactions); **generic webhooks**; Linear; Sentry; PagerDuty.
- Configured via the Agents Window, cursor.com/automations, or the `/automate` skill.
- Each run spins a cloud sandbox, uses your configured MCPs and models, verifies its own output, and has a **memory tool** that persists learning across runs.
- For cron/Slack triggers it can run **without a repository** at all — e.g. "every two hours, read data and post results."
- **Billed as cloud-agent usage** against your pool.

### How it pairs with GitHub Actions

Separately from Automations, there is **Cursor CLI (`cursor-agent`)** which runs headless in CI ([docs](https://cursor.com/docs/cli/github-actions), [headless docs](https://cursor.com/docs/cli/headless)). Install via curl, authenticate with `CURSOR_API_KEY` stored as a repo secret, run with `-p/--print` for non-interactive output. You choose full autonomy (agent does its own git ops) or restricted autonomy (agent only edits files; deterministic workflow steps do the commit/push), with JSON permission rules. Service accounts for CI billing are **Enterprise-only**.

**Bottom line for your architecture:** Cursor Automations and Cursor CLI both bill through Cursor. For your nightly valuation refresh jobs, plain GitHub Actions cron calling OpenRouter directly is cheaper and keeps the data pipeline independent of your editor vendor. Use Cursor Automations for *repo hygiene* (PR triage, dependency bumps, "summarize what changed"), not for *running the valuation pipeline*.

## 2) Cline (VS Code extension)

- **Open source: yes, Apache License 2.0** ([cline/cline LICENSE](https://github.com/cline/cline/blob/main/LICENSE)), copyright Cline Bot Inc. ~1.5M VS Code Marketplace installs by April 2026, 59k+ GitHub stars.
- **BYOK is the default and is free.** Anthropic, OpenAI, Google, **OpenRouter**, AWS Bedrock, Google Vertex, Azure, plus local runtimes (Ollama/LM Studio). You pay providers directly; the extension takes nothing ([cline.bot/pricing](https://cline.bot/pricing)).

## 4) pi (pi.dev) — one paragraph

Pi is a **minimal terminal-only agent harness** (TUI), **MIT-licensed**, built by Mario Zechner at Earendil Inc. with community contributors ([pi.dev](https://pi.dev/)). Philosophy is "primitives, not features": the core ships four tools — read, write, edit, bash — and everything else is an extension. It supports **15+ providers** (Anthropic, OpenAI, Google, Azure, Bedrock, Mistral, Groq, Cerebras, xAI, Hugging Face…) and **arbitrary custom providers via `models.json`**, so OpenRouter is a first-class citizen in practice — there's a dedicated [`pi-freerouter` package](https://pi.dev/packages/pi-freerouter) that routes every request through OpenRouter's **free `:free` model tier**, plus community extensions for live OpenRouter spend overlays and free-only model sync. Extensions are TypeScript files dropped into `~/.pi/agent/extensions/` that can register tools, intercept commands, add slash commands and rewrite the system prompt; sub-agents, MCP, plan mode and permission gates are all **extensions, not built-ins**. It deliberately ships **no permission popups** — you're expected to sandbox it in a container or write your own gate. Also runs in print/JSON, RPC and embedded-SDK modes. **Do not make this your first tool.**

## RECOMMENDATION for you specifically

**Daily driver: Cursor Pro ($20, already paid). Do not add a second paid harness.**

Reasons that are specific to your situation, not generic:

1. **You are a beginner building a system you will not fully understand on day one.** The per-hunk diff review, the Source Control panel, and Plan mode (Shift+Tab → read the English plan → approve → execute) are the difference between learning and cargo-culting. Terminal agents (pi, Claude Code) hide this.
2. **Your architecture is a scheduled pipeline, and Cursor now covers the whole loop.** Automations (cron + webhook triggers, MCP access, memory across runs) plus Cloud Agents on GitHub plus BugBot plus `cursor-agent` in GitHub Actions means one vendor covers authoring, review, and orchestration. That is worth more to you than model-shopping.
3. **Privacy is a stated requirement and Cursor's default path is the private one.** Privacy Mode + ZDR with all providers + SOC 2 Type II / ISO 27001 / ISO 42001. Turn Privacy Mode ON in settings on day one (it is only default-on for Enterprise).
4. **Budget maths.** $200/mo total. Cursor Pro $20 + Neon (~$19 Launch) + Pinecone (~$25 Standard) ≈ $64, leaving ~$135/mo of OpenRouter tokens for the *pipeline itself*. Spending another $60 on Pro+ or $19 on Kilo Pass buys you nothing your actual bottleneck needs — your bottleneck is pipeline token spend and your own learning rate, not editor capability.

**Second tool (free, install it, use it sparingly): Cline.**
Not as a competing editor — as your **OpenRouter bench**. It lives in the same VS Code window, costs $0 (Apache-2.0), speaks OpenRouter natively, and its **per-mode model split** (expensive model for Plan, cheap open-weight for Act) is the cleanest place to *empirically test* which model your valuation pipeline should call in production. You will be writing TypeScript that calls OpenRouter from GitHub Actions; Cline lets you feel what GLM-5.3 or Kimi K3 actually does on your code before you hard-code a model ID into a workflow. Kilo is a reasonable substitute if you prefer its mode system or want the $20 first-top-up credit, but Cline's Apache-2.0 licence, larger install base and stabler API make it the safer second tool. **Skip pi entirely for now** — no permission gates, everything is an extension you'd have to write, and you have a valuation system to build.

**Is "open-weight models via OpenRouter" still meaningful inside Cursor? Essentially no.**
Three reasons: (a) you'd be paying $20/mo for included pools and then routing around them — pure waste; (b) Tab completion, Auto mode and Composer 2.5 stay on Cursor's models regardless, so you get a hybrid you can't reason about; (c) **BYOK voids Cursor's ZDR**, which directly contradicts your "private" requirement. The `https://openrouter.ai/api/v1/cursor` endpoint works, but it's an unofficial path Cursor can break in any release.

**The correct split:** open-weight models belong in your **runtime**, not your **editor**. Your valuation system's own LLM calls — filing summarisation, narrative-to-number extraction, Pinecone retrieval reranking, comps commentary — should hit OpenRouter directly from TypeScript in GitHub Actions, where GLM-5.3-Flash at **$0.075/$0.25 per M tokens** is ~40× cheaper than a frontier model and you control the prompts. Cursor stays on its included Composer/Grok pool for authoring the code. Cline is where you benchmark candidates for the runtime.

## What is the point of open-weight models — 6 honest lines

1. **Cost:** GLM-5.3-Flash on OpenRouter is $0.075/$0.25 per M tokens vs $1.25/$4.25 for Muse Spark 1.3 — a 17–40× spread that decides whether your nightly re-valuation of 500 tickers costs $3/month or $120/month.
2. **Privacy:** open weights are the only way to get *provable* non-retention — you can run them on your own hardware or a rented GPU where no third party ever sees a filing, a prompt, or your valuation logic; every hosted API, including via OpenRouter, is a trust relationship.
3. **Control/self-hosting:** you can pin an exact checkpoint forever, so your DCF outputs stay reproducible across years — closed models get silently deprecated and retired, which quietly invalidates backtests.
4. **Licence:** it varies and it matters — **GLM-5.3-Flash (320B total / 18B active) shipped 26 Aug 2026 under plain MIT**, while **full GLM-5.3 (753B) shipped 28 Aug 2026 under a custom licence** adding a security review for model-as-a-service operators above $10B revenue; **Kimi K3's weights opened July 2026 under a revenue-tiered licence**. For a private personal project all three are fine; read before commercialising.
5. **The capability gap is real but narrower than the price gap:** on **Artificial Analysis Intelligence Index v4.3 (published 7 Sept 2026)** the frontier is **Claude Fable 5.1 = 53** and **GPT-6 Astra = 53**, with **Claude Opus 5 = 51**; best open weights is **GLM-5.3 (max) = 45**, then **Kimi K3 (max) = 44** and **GLM-5.3-Flash = 42** — an **8-point absolute / ~15% relative** gap, concentrated in long-horizon agentic tasks (Terminal-Bench v4.0, AutomationBench-AA), not in the summarise-and-extract work that dominates a valuation pipeline.
6. **⚠️ Correction to your brief:** **Muse Spark 1.3 is not an open-weight model** — it is Meta's proprietary, API-served model released 3 Sept 2026 at $1.25/$4.25 per M tokens (with a $0.10/$0.20 "Contributor tier" that trades data rights for price); its **48 is the "max" reasoning config still in limited partner preview pending safety testing**, while the publicly available **xhigh config scores 45**. Meta has only open-weighted the separate 30B **Muse Glimmer** (Apache 2.0, Aug 2026). So the honest framing is: for your pipeline, GLM-5.3-Flash at 42 for ~$0.10/M blended is the workhorse, GLM-5.3 at 45 is the open-weight ceiling, and you reach for a frontier model only for the final narrative synthesis.

### Neon connection gotchas that apply to all of them

- **SNI is mandatory.** Neon routes by the TLS SNI field because the Postgres wire protocol carries no hostname. libpq ≥ 14 (Sept 2021) handles it; older/exotic drivers fail. Workaround: append `?options=endpoint%3D<endpoint-id>` to the URL, or prefix the password field with `endpoint=<endpoint_id>;` (this downgrades SCRAM to password auth but stays TLS-encrypted). ([Neon connection errors](https://neon.com/docs/connect/connection-errors))
- **Use the pooled host** (`ep-xxx-pooler.<region>.aws.neon.tech`) for BI tools — PgBouncer, `sslmode=require` (not `verify-full`), and only a short list of startup parameters allowed. Keep the direct endpoint for migrations.
- **Looker Studio specifically** needs the cert upload (`isrgrootx1.pem`) and an empty port field — this is the one tool with a non-obvious setup. ([Neon → Looker Studio](https://neon.com/docs/connect/connect-looker-studio))
- **Neon recommends a read replica for BI tools**, since dashboards fire long/heavy queries that would otherwise hit your primary compute. ([Neon + Metabase guide](https://neon.com/guides/metabase-neon))
- Because your pipeline already runs on **GitHub Actions**, the cheapest "scheduled refresh" is: Actions job computes valuations/Monte Carlo/accuracy metrics → writes materialised tables into Neon → the dashboard just does `SELECT`. That removes in-tool scheduling as a buying criterion for most of the table above.

### When you'd need a custom Next.js app instead

Build the app when **any** of these becomes true — not before:

- **Write-back.** You want to edit a WACC or growth assumption in the UI and have it re-run the valuation and persist. Every tool above is read-only over Neon.
- **More than one class of viewer.** Per-user auth with row-level scoping (you vs. friends vs. public), or you want to show it to someone without buying them a seat. Per-editor pricing punishes growth; a Next.js app's viewer cost is ~$0.
- **Embedding is the product.** You want the dashboard *inside* your valuation app rather than beside it. Hex/Deepnote/Metabase all put embedding behind Enterprise/Pro walls; at that point building it is cheaper.
- **Bespoke financial visuals.** DCF waterfall bridges, tornado/sensitivity charts, football-field valuation ranges — these need custom components (Recharts/visx/Observable Plot), not a chart picker.
- **You're stitching ≥3 tools together**, or the BI bill passes ~$75/month. Both are signals the tool stopped being leverage.
- **It's a portfolio piece.** A live Next.js app on Vercel demonstrates far more to an employer than a Hex link.

Until then: keep the valuation engine in TypeScript on GitHub Actions writing to Neon, and treat the dashboard as a **disposable read layer**. If you architect it as "Actions computes → Neon stores results → something draws them", swapping Hex for Next.js later is a weekend, not a rewrite.

### INDmoney: public API and scraping terms

**Yes — there is a real, public, free API, but it's the broking API, not a data API for the app.** INDmoney's broking arm INDstocks publishes the **INDstocks API Suite** at [api-docs.indstocks.com](https://api-docs.indstocks.com/faq/): REST + WebSocket covering order placement/modification/cancellation and GTT "Smart Orders", holdings/positions/real-time P&L, live quotes, 10+ years of historical OHLCV, and option chains with Greeks. ### Bloomberg headline RSS: is it within ToS?

**The feeds work, but Bloomberg has never granted written permission for automated consumption, so this is a grey area you should treat conservatively — not a clean "yes".** I verified on 14 Sep 2026 that `https://feeds.bloomberg.com/markets/news.rss` 301-redirects to `https://www.bloomberg.com/feeds/markets/news.rss` and returns a valid RSS channel ("Bloomberg Markets") with same-day items, carrying the notice `Copyright 2026 BLOOMBERG L.P. ALL RIGHTS RESERVED` and **no feed-level licence grant or usage terms**. Bloomberg's [Terms of Service](https://www.bloomberg.com/notices/tos/) contain **no RSS carve-out**: they permit downloading material and one print copy for personal, noncommercial use, prohibit framing Bloomberg pages without written permission, and bar the use of any "scraper, robot, bot, spider, data mining" device absent express written consent. An RSS endpoint is, by design, published *for* automated readers, and your intended use — a private, single-user system polling a few times a day, storing only headline + link + timestamp + your own derived signal, never storing article text, never redistributing, never framing — sits at the most defensible end of that clause and is plainly personal and non-commercial. But the blanket automation prohibition means Bloomberg could still characterise it as a breach; this is a contract/ToS question rather than a settled copyright one (bare headlines are generally thin on copyright), and the risk of enforcement against a low-volume personal reader is low but not zero. **Practical guardrails:** poll no more than a few times daily and honour `Last-Modified`/`ETag` caching; send an honest descriptive User-Agent; check `bloomberg.com/robots.txt` before you start and respect it; store titles + URLs + timestamps only (drop `<description>`); keep the output private and never republish; and **don't let Bloomberg be load-bearing** — anchor the core news signal on sources with explicit machine-access policies (SEC EDGAR full-text search and its filing RSS, with its published fair-access rate limit, is the obvious one for a Damodaran-style system), with Bloomberg as an optional colour layer you can drop. If this ever turns commercial or public-facing, get written permission or a licensed feed. I'm not a lawyer and this isn't legal advice.

### The pipeline it implements

### The 3P gate

From `/blog/2014/07/possible-plausible-and-probable-big.md` (2014‑07‑16): "the difference in market size in the narratives boils down to a simple calculus of what is probable, what is plausible and what is possible… Not everything that is possible is plausible, and not all plausible opportunities make the transition to the probable." The check on weakest links: "The 3P tests forces you to think through the weakest links in your story, starting with whether any part of your story crosses the line into the impossible (fairy tale)" (`/New_Home_Page/inv4E/inv4edquesanswrs.md`). Memo schema: each claim carries `p3_class ∈ {possible, plausible, probable}`; only `probable` claims may set a base‑case input, `plausible` claims may set a scenario, `possible` claims are recorded and valued at zero.
