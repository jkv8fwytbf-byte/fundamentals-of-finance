# PART 1 — Bloomberg: what the "API Library" actually is, and whether you can touch it

## 1.1 What is on the API Library page

Source: https://professional.bloomberg.com/support/api-library/ (fetched 2026-09-14)

The page is a plain **download index for the BLPAPI SDK**, currently **v3.26.8.1**:

| Platform | Languages offered |
|---|---|
| Windows | Java, C# (.NET), C++ |
| Linux | Java, C++ |
| macOS ARM (**marked Experimental**) | Java, C++ |
| Python | via `pip` — wheels for Windows, macOS ARM, Linux |
| C# (.NET) **FFI** (**Experimental**) | via NuGet |

Also on the page: BLPAPI Developer's Guide (C++/Java/C#), reference docs, Core User Guide, and a **Schema Downloader** tool (Windows + Linux). Everything ships as `.zip` / `.tar.gz` direct downloads.

**The SDK download is free and unauthenticated. The data behind it is not.** BLPAPI is a proprietary binary transport library; with no entitlement it connects to nothing.

## 1.2 The entitlement statement — verbatim

The page carries this notice (I pulled it from the raw HTML; it appears on **both** the Linux and macOS ARM sections):

> "These Bloomberg API libraries cannot be used by Bloomberg Professional terminal users (which use the Desktop API). They are only compatible with the Bloomberg Server API and B-Pipe data feed products."

Read that carefully — it is **not** saying "anyone can use these." It is saying the Linux/macOS builds are the *server-side* builds, which require **SAPI or B-PIPE**. Terminal users get data through the **Desktop API (DAPI)** instead, which is Windows-only and rides the locally logged-in Terminal.

## 1.3 The four entitlement paths (all require a contract)

| Product | What it is | What it requires | Who it's sold to |
|---|---|---|---|
| **Desktop API (DAPI)** | BLPAPI talking to `bbcomm`, the local Terminal process | An **active, logged-in Bloomberg Professional Terminal** on the same machine. The app **inherits the Terminal user's entitlements** automatically. Windows in practice. | Terminal subscribers only |
| **Server API (SAPI)** | Same data, server-side, no desk attached | An **active Bloomberg Professional service subscription** + signed agreement. Bloomberg's own page: data "is only delivered to Bloomberg users" with an "active Bloomberg Professional service session" and biometric login | Institutions. Sales-led. No published price ([SAPI page](https://professional.bloomberg.com/products/data/data-connectivity/server-api/)) |
| **B-PIPE** | Consolidated real-time normalized market data feed, incl. non-display use | Enterprise contract; per-exchange redistribution fees | Firms |
| **Data License / DL REST** | Bulk + reference data, EOD pricing; ~50M securities, ~56k fields; REST surface behind the Bloomberg Enterprise Console | Enterprise contract | Firms |

Every one of these needs **a signed licensing agreement**. There is no self-serve signup, no public trial, no API key you can generate.

## 1.4 Can a bloomberg.com Digital / All Access subscriber use ANY of it?

**No. None of it. Zero programmatic market data.** Evidence, stacked:

1. **The API Library page itself** scopes the libraries to Terminal (DAPI), Server API, and B-PIPE — three enterprise entitlements. A news subscription is none of them.
2. **The SAPI product page** states data is only delivered to users with an "active Bloomberg Professional service session." A bloomberg.com login is not a Bloomberg Professional session — different product, different identity system.
3. **The developer surfaces are gated.** `developer.blpprofessional.com` and `console.blpprofessional.com` (where the DL REST API reference lives) require enterprise credentials. There is no consumer developer portal.
4. **Bloomberg publishes no public machine-readable API spec** — no OpenAPI, no GraphQL schema, no MCP server, no public API catalog entry. Access is contract-based and sales-led with no public trial.
5. **What bloomberg.com Digital/All Access actually buys** is editorial: unlimited bloomberg.com + app access, Businessweek, subscriber newsletters. Reported 2026 pricing ~**$34.99–$44.99/month** (sources vary; Bloomberg's own pages return HTTP 403 to automated fetches, so treat the exact figure as approximate and check the live page). Nothing in the product description mentions data export, bulk download, or API.

**Verdict: a bloomberg.com subscription is a magazine subscription. It carries no data entitlement whatsoever.**

## 1.5 Prices for the things that DO give programmatic access

- **Bloomberg Terminal (single seat): ~$31,980/user/year** (~$2,665/mo) as of 2026. Multi-terminal: **~$28,320/seat/year**. Typically a **2-year minimum commitment**, billed quarterly in advance. A **6.5% increase** applied to subscriptions renewing on/after Jan 1, 2025. Real first-year cost often quoted at **$33k–$35k** once the keyboard (~$300), install, and data add-ons land.
  - Sources: [costbench.com](https://costbench.com/software/financial-data-terminals/bloomberg-terminal/), [godeldiscount.com](https://godeldiscount.com/blog/bloomberg-terminal-cost-2026), [NeuGroup on the 6.5% hike](https://connect.neugroup.com/public/blogs/bloomberg-terminals-how-much-more-youll-pay-next-year)
- **Data License / B-PIPE / SAPI: no list price published.** Contract-negotiated on data fields, exchanges, redistribution rights, and number of consuming applications. The same 6.5% 2025 uplift applied to data licenses and real-time data services. Realistically five-to-six figures annually, plus exchange fees. Bloomberg does publish a real-time data fee schedule PDF ([BDRSL Data Fees Public Disclosure 2025](https://assets.bbhub.io/professional/sites/27/BDRSL-Data-Fees-Public-Disclosure-2025-FINAL.pdf)) but it is exchange-fee detail, not a product price list.
- **"Bloomberg for individuals" API in 2026: does not exist.** No consumer tier, no hobbyist tier, no student API. Bloomberg Anywhere is a Terminal-license mobility add-on, not a cheaper tier.

## 1.6 What Bloomberg DOES publish for free, consumer-facing

I verified these live today (2026-09-14), unauthenticated:

**RSS — yes, and it works.** `https://feeds.bloomberg.com/<section>/news.rss` returns valid RSS 2.0 XML. Confirmed HTTP 200 with fresh content (`lastBuildDate: Mon, 14 Sep 2026`, `Copyright 2026 BLOOMBERG L.P.`):

| Section | Status |
|---|---|
| `markets` | 200, ~15 KB |
| `technology` | 200, ~15 KB |
| `politics` | 200, ~16 KB |
| `economics` | 200, ~7 KB |
| `industries` | 200, ~7 KB |
| `bview` (Opinion) | 200, ~11 KB |
| `wealth` | 200, but only ~1 KB — near-empty |
| `businessweek` | 200, but only ~1 KB — near-empty |
| `green` | **404** |

**Caveat that matters:** these are **headline + short description + link only**. No full article text, no structured financial data, no tickers-as-fields. They are undocumented and unversioned — Bloomberg has never formally supported them, and the `green` 404 plus the near-empty `wealth`/`businessweek` feeds show they rot without notice. Fine for a news-sentiment signal; useless as a data source.

**Newsletters — yes, free ones exist.** `bloomberg.com/account/newsletters` offers free newsletters (Morning/Evening Briefing, Markets Daily, Matt Levine's *Money Stuff*). Some are subscriber-gated (e.g. the Odd Lots newsletter is subscribers-only). Email, not a feed — you'd need to parse a mailbox.

**Podcasts — yes.** Standard podcast RSS (Odd Lots etc., served via omnycontent).

Separately, Bloomberg launched **customizable Real-Time News Feeds** (machine-readable news + analytics) in **March 2026** — but that is an *enterprise* product sold alongside Terminal/Enterprise data, not consumer.

## 1.7 Plain conclusion for a consumer subscriber

> **Bloomberg gives you nothing programmatic.** Your bloomberg.com subscription grants read access to a website. The BLPAPI SDK is free to download but is inert without a Terminal (~$32k/yr), SAPI, B-PIPE, or Data License contract — all enterprise, all sales-led, all requiring a signed agreement, none available to an individual at any price you'd consider. There is no 2026 individual-tier Bloomberg API.
>
> **Do not design any part of your valuation system around Bloomberg.** The only legitimately free Bloomberg surface is the undocumented `feeds.bloomberg.com/<section>/news.rss` headline feeds and free email newsletters — suitable at most as a *news-event* signal, never as fundamentals. Get your Damodaran inputs from SEC EDGAR (free, structured XBRL, company facts API), Damodaran's own NYU datasets (free, updated each January), FRED (free, risk-free rates), and a paid fundamentals vendor if you need non-US coverage. That is where your ingest budget belongs.

**Storage overage:** artifacts/Packages **$0.25/GB/month**; Actions cache **$0.07/GB/month**.

**Two billing traps:**

1. **Larger runners never use your included minutes.** GitHub docs: *"Larger runners are always charged for, even when used by public repositories or when you have quota available."* The moment you put a 4-core or 8-core label in `runs-on`, you pay from minute one.
2. **GitHub rounds each job up to the whole minute.** Fifty 20-second jobs cost 50 minutes, not 17. This is the single biggest waste source for matrix-heavy ingest workflows.

**On multipliers — flag as uncertain.** The historical model charged Windows at 2× and macOS at 10× against your included-minute pool. GitHub's current reference page lists explicit per-minute dollar rates and **no longer states multipliers**, while several third-party 2026 pages still cite Windows 2× / macOS 10×. I could not resolve this cleanly. It doesn't affect you — **run everything on Linux x64** and the question disappears.

## 2.3 Do scheduled workflows auto-disable on a PRIVATE repo?

**GitHub's docs say the rule is public-only.** Verbatim from [events-that-trigger-workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows):

> "In a public repository, scheduled workflows are automatically disabled when no repository activity has occurred in 60 days."

Private repositories are **not covered by that sentence**. So on paper: **your scheduled ingest jobs on a private repo will not auto-disable.**

**But treat this as "probably safe, verify empirically."** Community reports conflict — some users report private repos being hit too, and there's a known related bug where scheduled-workflow disabling also disables the workflow's *non-schedule* triggers ([discussion #32197](https://github.com/orgs/community/discussions/32197)). Also note: only **new commits** reset the inactivity clock — releases, tags, issues, and merged PRs do **not** count.

**Two other schedule gotchas that will actually bite you:**

- **Minimum interval is 5 minutes.**
- **`schedule` runs get delayed — and dropped — under load, worst at the top of every hour.** GitHub's docs explicitly advise scheduling at a different minute. Use `17 6 * * *`, never `0 6 * * *`. For a nightly ingest pipeline this is the difference between "runs every day" and "silently skips a day a month."

**Recommendation regardless:** add a dead-man's-switch. Have the ingest job write a `last_run_at` row to Neon on success, and have a separate cheap check alert you if it goes stale. Never trust a cron you can't observe.

## 2.4 Blacksmith (blacksmith.sh)

**What it is:** drop-in replacement GitHub Actions runners on faster bare-metal hardware — you change one label and nothing else. They claim ~2× faster compute and 4× faster cache downloads, plus CI observability (run history, log search, SSH-into-running-job, metrics, test analytics). They also sell `[code]smith`, a cloud coding agent — ignore that for your purposes.

**Free tier: 3,000 minutes/month per organization** (priced as x64 2vCPU minutes). Higher-vCPU runners burn the free pool proportionally faster.

**Per-minute pricing** ([blacksmith.sh/pricing](https://www.blacksmith.sh/pricing), fetched 2026-09-14):

| Runner | $/min | vs GitHub |
|---|---|---|
| **Ubuntu x64 (2 vCPU)** | **$0.004** | 67% cheaper |
| **Ubuntu ARM** | **$0.0025** | 75% cheaper |
| Windows x64 | $0.008 | 60% cheaper |
| macOS M4 | $0.08 | 35% cheaper |

Add-ons: Docker layer caching **$0.50/GB/mo**, sticky disks **$0.50/GB/mo**, static IPs **$100/IP/mo**. Startup program (<100 employees, <$50M raised, or <5 years old) and a free OSS program exist.

**How to switch:** install the GitHub App at `app.blacksmith.sh`, then change `runs-on`. Their migration wizard opens the PR for you.

```yaml
jobs:
  build:
    runs-on: ubuntu-latest                  # before
    runs-on: blacksmith-2vcpu-ubuntu-2404   # after
```

Common mappings: `ubuntu-latest` → `blacksmith-2vcpu-ubuntu-2404`; `windows-latest` → `blacksmith-2vcpu-windows-2025`; `macos-latest` → `blacksmith-6vcpu-macos-latest`. **Update every job in the file** — partial migration silently leaves jobs on GitHub's meter.

**Full label set:** `blacksmith-{2,4,8,16,32}vcpu-ubuntu-{2404,2204}` and `-arm` variants (2–32 vCPU, 6–128 GB RAM); Windows `blacksmith-{2..32}vcpu-windows-2025` (**public beta**); macOS `blacksmith-{6,12}vcpu-macos-{latest,26,15}`.

### ⚠️ The blocker for you

From Blacksmith's own quickstart docs, verbatim (fetched 2026-09-14):

> "Blacksmith is limited to GitHub organizations and not available for personal repositories."

Your private valuation repo under a personal account **cannot use Blacksmith at all**. Their permission model inherits entirely from GitHub *org* structure (org admins, repo roles) — there's no personal-account path.

**The fix is free and takes two minutes: create a GitHub organization** (free tier), and put the private repo inside it. A Free *organization* also gets 2,000 Actions minutes/month for private repos. Do this on day one even if you never use Blacksmith — it costs nothing and keeps every third-party runner option open. Also note: if you later enable an org IP allowlist, you must allowlist Blacksmith's control-plane IPs.

**2026 changes:** nothing announced on their pricing page. Their public commentary focused on GitHub's Dec-2025 control-plane charge announcement.

## 2.7 Recommendation — cheapest reliable setup

**Do this, in order:**

**1. Put the private repo in a free GitHub organization from day one.** Costs $0. Free orgs get 2,000 private Actions minutes/month, same as a personal Free account. This is the single decision that keeps Blacksmith (and most alternatives) available to you later — and it's a painful migration to do after you've wired up secrets, environments, and OIDC.

**2. Start on GitHub-hosted `ubuntu-latest`, GitHub Free plan, $0/mo.** Don't optimise a bill you haven't received. Watch actual usage for 3–4 weeks in Settings → Billing.

**3. Add Blacksmith once you're consistently over ~3,000 min/month.** Install the app, run the migration wizard, change `runs-on: blacksmith-2vcpu-ubuntu-2404` everywhere. Their 3,000 free minutes plus ~2× speed means your realistic bill at 6,000 GitHub-equivalent minutes is **$0–$12/month**. Keep GitHub Free underneath as an instant fallback — reverting is a one-line label change, which is exactly why this is the low-risk choice.

**4. If you'd rather avoid a third party entirely:** GitHub **Pro at $4/mo** and stay on `ubuntu-latest`. Worst case $22/mo at 6,000 minutes. That is 11% of your $200 budget and requires zero extra vendors, zero extra secrets, zero extra failure modes. For a beginner, this is a completely defensible choice — the simplicity is worth more than the $10.

**Expected CI line item either way: $0–$25/month.** Your budget is not at risk from CI; it's at risk from model tokens and data vendors.

**Guardrails to set up now (these save more than any runner choice):**

- **Set a hard Actions spending limit** ($25) in org billing settings. A runaway retry loop in an ingest job is the realistic way you blow the budget. Do this before your first scheduled workflow.
- **`timeout-minutes` on every job.** Default is 360 minutes — a hung API call costs you ~$2.16 in silence.
- **`concurrency: { group: ..., cancel-in-progress: true }`** so pushes cancel superseded runs.
- **Cache the pnpm/npm store**, not `node_modules`. Cache storage is 10 GB free, then $0.07/GB/mo — cheap relative to minutes.
- **Beware per-job minute rounding.** A 20-job matrix of 15-second jobs bills 20 minutes. For ingest fan-out, batch inside one job rather than fanning out across matrix entries.
- **Schedule off the hour** (`17 6 * * *`, not `0 6 * * *`) — GitHub explicitly warns queued scheduled jobs can be *dropped* under top-of-hour load.
- **Don't burn CI minutes waiting on rate limits.** If an ingest job sleeps against a vendor's rate limiter, you're paying $0.006/min to do nothing. Chunk the work across runs, or move that specific job off Actions.
- **Add a staleness alarm.** Write `last_run_at` to Neon on each successful ingest; alert if it goes stale >36h. This covers you against the schedule-drop and any auto-disable ambiguity at once.

**Skip for v1:** RunsOn (you'd own AWS CloudFormation + spot capacity — real ops burden), Depot (monthly floor kills it at your volume), BuildJet (no free tier, otherwise identical to Blacksmith).

## 1. "Fine-tuning" at three levels

### 1a. Fine-tuning the HARNESS (pi) — this is the level you actually need

Think of pi as a new employee who is brilliant but has amnesia every morning. You cannot retrain their brain, but you can leave them a desk: a job description on the wall (AGENTS.md), a filing cabinet of procedures they open only when relevant (skills), a set of custom power tools (extensions), some pre-written memos (prompt templates), a locked room so they can't break the office (sandbox), and a phone to delegate to temps (sub-agents). None of this changes the model's weights — it changes what lands in the context window and what the model is allowed to do. For a valuation system this is where 95% of your quality comes from, and it costs $0. pi loads `AGENTS.md` (or `CLAUDE.md`) at startup from `~/.pi/agent/AGENTS.md`, then every parent directory, then the current directory; `AGENTS.override.md` in a directory replaces that directory's file, and `.pi/SYSTEM.md` / `APPEND_SYSTEM.md` replaces or appends the system prompt entirely. Skills live in `~/.pi/agent/skills/`, `~/.agents/skills/`, `.pi/skills/`, `.agents/skills/`, each as `<name>/SKILL.md` with required frontmatter `name` (≤64 chars, lowercase/hyphens) and `description` (≤1024 chars) — pi reads only names and descriptions at startup and loads the body on demand ("progressive disclosure"), so 40 skills cost you almost no tokens. Extensions are TypeScript modules in `.pi/extensions/*.ts` that call `pi.registerTool({ name, label, description, parameters, execute, renderCall, renderResult, promptSnippet })` and subscribe to events (`session_start`, `tool_call`, `before_provider_request`, `model_select`, `agent_end`, …). Model routing is per-session via `/model`, plus `defaultProvider`/`defaultModel`/`enabledModels`/`modelThinkingLevels` in `~/.pi/agent/settings.json` or `.pi/settings.json` (project overrides global, nested objects merge).

Practical mapping for your build: AGENTS.md = the Damodaran house rules (always separate operating from financing, never mix a licence class, every number cites a row id). Skills = `dcf-build`, `edgar-fetch`, `ocr-deck`, `wacc-estimate`. Extensions = `registerTool` wrappers for Neon SQL, Pinecone query, and the SEC EDGAR API so the model can't free-hand HTTP. Sandbox = Docker Sandboxes or Gondolin so a scraped page can never exfiltrate your keys.

### 1b. Prompt / context engineering

Prompt engineering is writing one good instruction; context engineering is deciding what the model sees at all — which is the harder and more valuable skill. The analogy: a prompt is the question on the exam; context is which textbooks, notes and past papers are on the desk. Anthropic's framing (29 Sep 2025) is "what configuration of context is most likely to generate the desired behaviour?", and it names **context rot**: as token count climbs, recall of any individual fact degrades. The discipline is to curate the smallest set of high-signal tokens, not to dump everything in. For valuation this means: never paste a 200-page 10-K; extract the eight line items you need into a DB row, then put the row in context with its citation.

### 1c. Fine-tuning an open-weight MODEL (fully outsourced)

Fine-tuning changes the model's weights so it *behaves* differently by default. The right analogy: you are not teaching the analyst new facts, you are teaching them your firm's memo template so hard they can't write it wrong. **Form, not facts.** Facts belong in Postgres and Pinecone, where they can be updated, audited and cited; baked-in facts go stale and cannot be cited. LoRA (Low-Rank Adaptation) trains a small adapter on top of a frozen base model, which is why it is cheap. You need roughly **500–1,000 high-quality examples** for a form task; quality and consistency matter far more than volume, and every example must be exactly the output you want. FinLoRA (arXiv 2505.19819, May 2025) is the best evidence for your domain: 19 financial datasets including four novel XBRL-analysis sets built from 150 SEC filings, five LoRA methods and five base LLMs, with LoRA delivering **+36% average** over base models and vanilla LoRA (8-bit, rank 8) scoring 74.74 vs 37.05 for base Llama 3.1 8B — a 37.7-point lift on tasks like XBRL tagging.

**2026 prices per run.** Together AI LoRA SFT is about **$0.48/M training tokens on ≤16B**, ~$1.50/M for 17–69B, ~$2.90/M for 70–100B. Fireworks publishes **$0.50/M for <16B LoRA SFT**, $3.00/M for 16–80B, $6.00/M for 80–300B, $10.00/M for >300B (DPO ≈ 2× SFT). Google Vertex supervised tuning bills training tokens = dataset tokens × epochs, and the tuned endpoint costs the same as the base model at inference. Unsloth is free on a Colab T4 (4-bit + LoRA fits a 7–8B model in 6–8 GB; 1k–10k examples ≈ 15–60 min). Do the arithmetic: 800 examples × ~1,500 tokens × 3 epochs ≈ **3.6M training tokens ≈ $1.80 on a ≤16B LoRA**. Ten experiments cost under $20. **The training run is never the expense — data curation and serving are.** A dedicated GPU endpoint left running at $2–10/hr will eat your entire $200/month in a weekend; insist on serverless LoRA inference billed at the base-model rate, or shut the endpoint down.

Deployment: OpenRouter's **BYOK** lets you plug your Together/Fireworks/Vertex key in and route through one API, charged at **5% of the equivalent OpenRouter cost, waived for the first 1M BYOK requests/month**. Routing a truly *private* custom endpoint through OpenRouter is an **Enterprise-plan** feature — so for a solo build, call the vendor's OpenAI-compatible endpoint directly and keep OpenRouter for the off-the-shelf models. Note the consolidation: Predibase was acquired by Rubrik (Jun 2025) and OpenPipe by CoreWeave (Sep 2025), so neither is the low-friction solo-dev option it was.

**Verdict for you: don't fine-tune in v1.** Do it only when you have 500+ logged, hand-corrected outputs from the running system and a measurable, repeated format failure (e.g. the model keeps mislabelling operating leases, or won't emit your DCF JSON schema). Then it's a $2 experiment.

## 2. OCR

OCR (Optical Character Recognition) turns a picture of text into text. Analogy: a PDF can be either a Word document or a photograph of a Word document — they look identical on screen, but you can select and copy text in one and not the other. Damodaran's lecture decks (e.g. `darksideextended13.pdf`) are largely exported slides: some pages carry a real text layer, but tables, chart labels and scanned inserts often do not, so a naïve `pdftotext` returns headings and loses the numbers you actually want. **Always check before you pay:** run `pdffonts file.pdf` (no fonts listed = image-only) and `pdftotext -layout file.pdf -` on a few pages; if the text is there, skip OCR entirely. Modern "OCR" services are vision-language models that also reconstruct layout, tables and reading order into Markdown — that structure matters more than raw character accuracy for RAG, because a table flattened into a word soup destroys the row/column relationship that makes a number meaningful.

**2026 prices:** Mistral OCR **$4 / 1,000 pages**, Mistral Document AI **$5 / 1,000 pages**, both roughly halved via the Batch API (official pricing page). Google Document AI runs ~**$1.50 / 1,000 pages** for basic OCR (dropping to ~$0.60 above 5M pages/month) but **$30 / 1,000** for Form Parser and custom extractors. AWS Textract is ~**$1.50 / 1,000** for plain text detection, **$15 / 1,000** for tables and **$50 / 1,000** for forms. A 100-page Damodaran deck therefore costs ~$0.40 on Mistral — irrelevant to your budget, so choose on output quality, not price.

**Checking quality:** the standard metrics are Character Error Rate and Word Error Rate (edit distance ÷ reference length); OmniDocBench uses normalised edit distance across text, formulas, tables and reading order. For a solo build, do three cheap checks instead: (1) hand-key ground truth for 3–5 representative pages and compute CER; (2) **arithmetic round-trip** — if an OCR'd table's columns don't sum to its stated total, the OCR is wrong, and this catches the failures that matter (a misread `8` as `3`); (3) confirm page count and detect silently-dropped pages. Research in 2026 shows OCR that scores well on character accuracy can still wreck downstream retrieval when structure is lost, so test the pipeline end-to-end, not the OCR in isolation.

## 3. Web crawling vs search APIs vs scraping

Three different jobs. **Search API**: you ask a question, you get back ranked URLs (and often the page text) — like asking a librarian. **Crawling**: you start at one URL and follow links breadth-first to enumerate a whole site — like walking every aisle of the library and noting every book. **Scraping**: you fetch one known page and extract specific fields from its HTML — like opening a known book to page 42 and copying the table. You almost always want search → crawl only when you must enumerate → scrape only when the data isn't in an API.

**Legality, plainly.** In the US, scraping *publicly accessible* pages is generally not a Computer Fraud and Abuse Act violation: *hiQ Labs v. LinkedIn* (9th Cir.) held that where a page is open without credentials there is no authorisation gate to breach, and *Van Buren v. United States* (2021) narrowed "exceeds authorized access" to data you were never entitled to see. But hiQ won the CFAA point and still **lost on breach of LinkedIn's User Agreement** (Nov 2022, ending in a consent judgment), and *Meta v. Bright Data* confirmed contract claims survive where CFAA claims fail. So: CFAA is rarely your risk; **ToS, copyright, and privacy law (GDPR/CCPA) are**. `robots.txt` (standardised as RFC 9309) is voluntary and no statute criminalises ignoring it, but courts cite non-compliance as evidence of bad faith — honour it. For your project the good news is that you mostly don't need to scrape: **SEC EDGAR publishes free official JSON APIs and full-text search** (you must send a descriptive `User-Agent` with contact info and stay under ~10 req/s), and Damodaran's NYU Stern pages are static files you may fetch directly. Reserve the paid tools for news, transcripts and one-off gaps — and record a `licence_class` on every row you ingest (see topic 7).

**2026 prices.** Firecrawl (official): free 1,000 credits/month; Hobby $16/mo annual (5,000); Standard $83/mo (100,000); Growth $333/mo (500,000); Scale $599/mo (1,000,000) — 1 credit per page for scrape/crawl/map, **+4 credits for JSON extraction**, Stealth Mode 5×. Exa (official): $7 / 1,000 searches, $1 / 1,000 pages of content per content type, $5 / 1,000 answer calls, $12–15 / 1,000 deep-search, **$20 free credits plus $10/month free**. Parallel: Search ~$1–5 / 1,000, Extract $0.001/request, Responses $0.01–0.25/request, **$5 free credits monthly**. Apify: Free plan with $5 of usage; Starter $29/mo; Scale $199/mo; compute unit ≈ $0.20 (Starter) → $0.13 (Business), where 1 CU = 1 GB of RAM for 1 hour. Bright Data Web Unlocker: ~**$1.50 / 1,000 successful requests** pay-as-you-go (lower on commitment; failures not billed) — this is the anti-bot heavyweight you use only when a site blocks you. Playwright is free and open source; you pay only in compute (GitHub Actions minutes) and maintenance, and it's the right tool for login-gated or JS-heavy pages you're licensed to access. For a $200/month private build: Exa or Parallel free tiers + Firecrawl free/Hobby + Playwright in Actions covers v1.

## 4. Sub-agents / multi-agent

A sub-agent is a second LLM session your main agent spawns: its own context window, its own system prompt, its own restricted tool set. It does a job and hands back a short summary — the parent never sees the 200,000 tokens the sub-agent burned. Analogy: hiring a research assistant who reads the entire 10-K in a separate room and returns a one-page memo; your desk stays clean. Three real benefits: **parallelism** (ten filings processed at once instead of sequentially), **fresh context** (each sub-agent starts clean, dodging context rot), and **cheap routing** (a fast small model does grep-and-summarise work while the expensive model does the reasoning). The cost is straightforward and easy to underestimate: each sub-agent pays for its own system prompt and tool definitions, so a 5-way fan-out is roughly 5× the token spend of one call, plus the parent's cost to fan out and merge.

**pi-subagents specifics.** Install with `pi install npm:@tintinweb/pi-subagents`; requires pi ≥ 0.84.0. Custom agent types are Markdown files at `.pi/agents/<name>.md` with YAML frontmatter: `tools` (built-in names or `ext:` selectors), `model` (fuzzy `"haiku"`/`"sonnet"` or `provider/model-id`), `thinking` (off→max), `max_turns`, `memory` (project/local/user), `isolation: worktree` for git-isolated runs, and `allowed_subagents` for nested delegation. Three defaults ship: `general-purpose` (all tools, parent's model), `Explore` (read-only, haiku, fast codebase scans) and `Plan` (read-only, parent's model). Persistent settings live in `~/.pi/agent/subagents.json` or `.pi/subagents.json`: `maxConcurrent` defaults to 10 with excess queued, `backgroundByDefault: true`, nested agents capped at depth 2. Agents run in the background with a live widget, support mid-run steering and session resumption, and there's a `SubagentWorkflow` tool for deterministic JS orchestration (`agent()`, `parallel()`, `pipeline()`, `phase()`) in a sandboxed `node:vm`. **Turn on `showCost` and `reportUsage` immediately — both default to off**, and on a $200/month budget you want sub-agent spend rolled into your session totals from day one.

**When NOT to use them.** (1) Sequentially dependent work — step 2 needs step 1's full output, and summarisation loses it. (2) Shared mutable state — sub-agents can't see each other, so two agents writing the same DCF row will silently conflict. (3) Small tasks where the handoff overhead exceeds the work. (4) **Anything whose numbers you must audit** — a prose summary is lossy; make sub-agents write structured rows to Postgres with citations and return only row ids, so the parent reads facts from the DB, not from a paraphrase. (5) When you're debugging: one linear session is far easier to read than ten interleaved transcripts.

## 5. Benchmark literacy for artificialanalysis.ai

Benchmarks are standardised exams for models. The site's headline **Intelligence Index (v4.3)** is a weighted composite of 10 evaluations in four groups: **Agents 30%** (AA-Briefcase 15%, GDPval-AA v2 10%, AutomationBench-AA 5%), **Coding 20%** (Terminal-Bench v4.0 10%, SciCode 10%), **General 30%** (AA-Omniscience 15%, GDP.pdf 10%, AA-LCR v1.1 long-context 5%), and **Scientific Reasoning 20%** (Humanity's Last Exam 10%, CritPt 10%). The **Coding Agent Index (v1.5)** is different in kind: it is the equal-weighted mean of DeepSWE v1.1, Terminal-Bench 4.0 and SWE-Atlas-QnA, each scored as pass@1 averaged over three attempts per task — and critically it benchmarks **harness + model pairs**, not models alone, because the scaffold matters as much as the weights. **AA-Omniscience** is a 6,000-question knowledge-and-hallucination benchmark over 42 topics in six domains; its Omniscience Index runs **−100 to +100**, rewarding correct answers, penalising confident wrong ones, and crediting abstention — at launch, 33 of 36 models scored below zero, i.e. were more likely to hallucinate than to be right on hard questions. The **Search Index** benchmarks *search API providers*, not models: a fixed "Stirrup" agent harness with `web_search` and `web_fetch`, 25 turns, a fixed candidate model, scoring the equal-weighted mean of DeepSearchQA (F1), BrowseComp and an AA-Omniscience subset.

Speed and money: **time to first token (TTFT)** is seconds from request to the first token — and for reasoning models that's the first *reasoning* token, so a model can have a fast TTFT and still make you wait 40s for a useful word. **Output tokens per second** is throughput after the first token. **Cost per task** is the weighted-average USD to complete one Intelligence Index task, computed from provider-reported token counts and live cache-hit rates — this is the number that actually maps to your bill. **Blended price** is a single $/M figure assuming a **7:2:1 ratio of cache-hit : input : output tokens**.

**Traps.** (1) *Index inflation* — labs optimise for the composite; ignore the headline and read the sub-benchmark matching your job. For valuation that's AA-Omniscience (does it make up numbers?) and AA-LCR (can it hold a 10-K?), not HLE. (2) *Provider vs model pricing* — the same open-weight model on OpenRouter is served by many providers at different prices, speeds, context limits and **quantizations**; the leaderboard row is often the reference endpoint, not the one you'll be routed to. Pin the provider. (3) *Reasoning tokens are billed as output* — a "cheap" $0.30/M model that emits 8,000 thinking tokens per answer costs more than a $3/M model emitting 300. Always compare **cost per task**, never $/M. (4) *Blended price assumes a cache-hit ratio you may not achieve* — if your prompts change every call, your real cost can be several times the blended figure; keep a stable prefix. (5) *Harness dependence* — a model topping the Coding Agent Index under one scaffold may underperform under pi.

**Picking per job**, as a routing table in `settings.json`: cheap/fast model for OCR post-clean, classification and skill triage; high AA-Omniscience + AA-LCR model for filings extraction and any step that emits a number; top Coding Agent Index model for writing your TypeScript; the Search Index leader for the web tool.

## 6. Vector search / RAG in plain words — a 10-minute mental model

Imagine a library where every paragraph has been assigned coordinates in a 1,500-dimensional space, positioned so that paragraphs *about the same thing* sit near each other regardless of wording. That's the whole idea. A **chunk** is one paragraph-sized slice of a document (256–512 tokens with ~15% overlap is the 2026 default; overlap stops a sentence being cut in half). An **embedding** is that chunk's coordinates — a list of numbers produced by an embedding model. **Cosine similarity** measures the angle between two coordinate arrows: 1.0 means "pointing the same way" (same meaning), 0 means unrelated; you embed the question the same way and grab the nearest chunks. But nearest-in-space ≠ most useful, so you over-fetch (say top 50) and run a **reranker** — a slower, smarter model that reads the question and each candidate *together* and re-scores them, keeping the best 5–8. **Hybrid search** runs keyword search (BM25 — literally "does the word 'goodwill impairment' appear?") alongside vector search and fuses the results, which matters enormously in finance where exact tickers, tags and line-item names must match literally and embeddings are fuzzy about them. A **citation** is the document id + page + character offset you store as metadata on every chunk, so every claim the model makes can be traced back to a source you can open.

For this project, one rule above all: **retrieval finds the paragraph; the database holds the number.** Never let a figure travel from a retrieved chunk into a valuation without being written to a Postgres row alongside its citation and licence class. RAG is for narrative and context (risk factors, segment commentary, Damodaran's reasoning); Postgres is the system of record for anything you multiply.

## 7. Databases for a beginner

**Postgres** (PostgreSQL) is a free, open-source relational database: a program that stores data in tables and answers questions in SQL. A **table** is a spreadsheet with a fixed, enforced schema; a **row** is one record (one company-year, one assumption, one source document); a **column** has one type. **NOT NULL** means the column can never be empty — the database itself refuses the write. A **CHECK constraint** is a rule the database enforces on every insert, e.g. `CHECK (tax_rate >= 0 AND tax_rate <= 1)` or `CHECK (licence_class IN ('public','vendor_redistributable','internal_only','prohibited'))`. Analogy: constraints are the guard rails on a mountain road — annoying while you drive, and the reason you're alive. In an LLM-driven system they are essential, because the model *will* eventually try to write a 340% tax rate, and you want that rejected by the database rather than discovered in a valuation.

**System of record** means: for any given fact, exactly one place is the truth, and everything else is a copy or a cache. Your Postgres rows are the system of record; Pinecone, model context and Markdown reports are derived views that can be rebuilt. **Migration** is a versioned script that changes the schema (add a column, add a constraint), checked into git and applied in order, so every environment has the same shape — the database equivalent of a commit. A Neon **branch** is a copy-on-write clone of your entire database created in seconds without duplicating storage, exactly like a git branch: test a migration on `dev`, let a CI run get its own throwaway database, drop it after. Neon's free tier gives 0.5 GB storage, 100 compute-hours/month, scale-to-zero and one project; paid compute is ~$0.106/CU-hour (Launch) or $0.222/CU-hour (Scale), storage $0.35/GB-month, with extra branches ~$1.50/branch-month prorated — comfortably inside $200/month for this workload.

**Why a licence class on every row.** Different data carries different redistribution rights, and rights attach to *facts*, not to files. Bloomberg's terminal agreements license data to the individual subscriber for their own use; extracting it into a downstream store, redistributing it, or feeding it into models requires a separate data licence (B-PIPE / Data License), and the terminal's own terms prohibit bulk extraction. So if a single Bloomberg-derived beta lands in your `assumptions` table with no label, and that table later feeds a report you share or a model you fine-tune, you cannot prove which numbers were safe — and the practical consequence is that the *entire table* becomes unshareable. Analogy: allergen labels belong on every ingredient, not just the finished dish; once the cake is baked you can't tell which flour had nuts. So: `licence_class TEXT NOT NULL CHECK (licence_class IN (...))` on every fact table, plus `source_url`, `retrieved_at`. Now `WHERE licence_class = 'public'` produces a provably shareable output, and SEC/EDGAR (public domain) and Damodaran's freely published datasets flow through cleanly.

## 8. TypeScript for someone who knows Python — the 8 things that bite

1. **`null` AND `undefined`.** Python has one `None`; JS has two empties — `undefined` (never set) and `null` (explicitly nothing). Turn on `strictNullChecks` (included in `strict`), use `?.` for optional chaining and **`??` not `||`** for defaults, because `||` also fires on `0` and `""` — which in a valuation system silently turns a real 0% growth rate into your fallback.
2. **`===` not `==`.** `==` coerces types (`'' == 0` is `true`, `'1' == 1` is `true`). Use `===` always; there is no reason to use `==` except `x == null` to catch both empties.
3. **`number` is IEEE-754 float64. There is no int and no Decimal.** `0.1 + 0.2 !== 0.3`. Never hold money or share counts in `number` for accumulation — use integers in minor units, or `decimal.js`. Related gotcha: `node-postgres` returns Postgres `NUMERIC` and `BIGINT` as **strings** on purpose, to avoid exactly this precision loss. Don't "fix" it with `Number()`.
4. **`async`/`await` is everywhere and not optional.** Nearly all I/O returns a Promise. Forgetting `await` doesn't error — it gives you a `Promise` object that looks fine until it's `NaN` three functions later; enable `@typescript-eslint/no-floating-promises`. Use `Promise.all` for parallel fetches (no GIL, but also only one thread — it's an event loop, not threads).
5. **Modules: ESM vs CommonJS.** Set `"type": "module"` and you're in ESM: `import`/`export`, no `require`, no `__dirname` (use `import.meta.url`), and under `moduleResolution: "NodeNext"` **relative imports must carry a `.js` extension even when the file is `.ts`**. This one detail causes most first-week build failures.
6. **`strict` mode, and the fact that types vanish at runtime.** TypeScript erases all types when compiling — a typed API response is a *promise*, not a check. `strict: true` (on by default in TS 6.0) plus `noUncheckedIndexedAccess` gets you Python-plus-mypy-level safety; validate every external input (API JSON, OCR output, LLM output) with **Zod** at the boundary so runtime reality matches the types.
7. **pnpm workspaces instead of venvs.** There is no per-project interpreter; you get a `node_modules` folder. A monorepo is a `pnpm-workspace.yaml` listing package globs, with internal deps written `"@you/core": "workspace:*"`. pnpm's strict, symlinked layout means an undeclared dependency fails loudly — good, but surprising if you're used to a flat site-packages.
8. **Vitest is pytest.** `describe`/`it`/`expect` instead of `test_*` functions and bare `assert`; `vi.mock()` for monkeypatching; `--coverage` built in. It runs TypeScript natively — you do not need ts-jest or a build step for tests.
